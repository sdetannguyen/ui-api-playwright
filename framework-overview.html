ui-api-playwright

A TypeScript-based test automation framework for UI and API tests. Three-layer architecture built on Playwright's native primitives — fixtures, request context, and auto-wait.

TypeScript 5.3 Playwright 1.60 Node 18 ESLint 8 Husky 8 CircleCI GitHub Actions

Structure

Three strict layers. Infrastructure owns config and credentials. lib/ owns page objects, API clients, and the fixture wiring. Tests are thin specs that import from lib/fixtures only.

Layer 1

Infrastructure infrastructure/

  • env.config.ts — all URLs, isCI flag
  • credentials.ts — auth from env vars
  • No Playwright imports here
Layer 2

Abstraction lib/

  • BasePage — abstract, page constructor
  • ReqresHomePage, PracticeAutomationLoginPage
  • ReqresApiClient — typed CRUD methods
  • pages.fixture.ts — test.extend() wiring
  • index.ts — single import point
Layer 3

Tests tests/

  • setup/auth.setup.ts — storageState auth
  • ui/reqres-home.spec.ts — UI specs
  • api/reqres-users.spec.ts — API specs
  • Import only from lib/fixtures

Intent

Same three-layer intent as the Selenium counterpart — infrastructure, abstraction, tests — but expressed in TypeScript idioms. The test.extend() fixture pattern replaces inheritance: tests declare exactly what they need and receive it injected, making dependencies explicit and the test body free of setup noise.

The secondary intent is to show that API and UI testing can live in the same project, same language, same fixture system — without the overhead of a separate RestAssured dependency or a different language for API tests.

What Works Well / What Doesn't

Works Well

  • Auto-wait — nearly zero explicit wait code needed
  • storageState auth — login once, reuse across all tests
  • test.extend() — fixtures compose cleanly, no inheritance chain
  • Unified API + UI — single import from lib/fixtures
  • Trace on first retry — failure debugging without extra tooling
  • TypeScript — types catch refactoring mistakes at compile time

Doesn't Work Well

  • ESLint not in CI — only runs via Husky pre-commit, can be bypassed with --no-verify
  • No security scanning — no Trivy or equivalent in CI
  • GHA only triggers on main/master — feature branch pushes skip GHA, only CircleCI runs
  • GeeksForGeeksHomePage exists with no test — dead abstraction
  • retries: 2 on CI can mask genuine flakiness
  • No unit tests for infrastructure/fixtures layer

What's Missing

  • High ESLint in CI — linting only runs via Husky locally. A developer who pushes with --no-verify skips it entirely. Add an ESLint job to the GHA workflow.
  • High Security scanning — no Trivy or npm audit in CI. Dependencies like axios, googleapis, and twilio are not scanned for CVEs.
  • High GHA triggers on all branches — currently only runs on main/master. Feature branch pushes get CircleCI only. Change to branches: ["**"] for full coverage.
  • Medium Test for GeeksForGeeksHomePage — page object exists, no spec. Either add a test or remove the dead code.
  • Medium Video on failure — trace is captured on first retry but no video. Add video: 'on-first-retry' for richer failure context in CI.
  • Low Unit tests for fixtures — pages.fixture.ts wiring and env.config.ts defaults are untested. A unit test catches misconfiguration before it shows up as a mysterious test failure.
  • Low ReqresHomePage heading locator — currently uses "Your backend, live in your browser." which may not match the live site heading. Should be verified against the actual page.

Tradeoffs

DecisionWhy this choiceCost
TypeScript Type safety catches refactoring mistakes; same language as most modern frontend teams Build step required; slightly more complex toolchain than plain JS
test.extend() over BaseTest inheritance Composition — tests declare exactly what they need; easier to test fixtures in isolation Mental model shift for engineers coming from xUnit/TestNG inheritance patterns
Built-in request context for API tests No extra dependency; API and UI tests share the same fixture system Less fluent DSL than RestAssured for complex request building
storageState for auth Login runs once per suite, not once per test — faster, less flakiness risk Session can expire mid-run; need a refresh strategy for long suites
Dual CI (CircleCI + GHA) CircleCI for branch pushes, GHA for PR gate — both already exist Two configs to maintain; easy to drift out of sync
Husky for linting (not CI) Fast feedback at commit time; catches issues before push Can be bypassed with --no-verify; not a hard gate
retries: 2 on CI Reduces noise from transient CI failures (network, timing) Masks genuine flakiness — a test that passes on retry 3 is still a flaky test

Playwright vs Selenium

Playwright (this repo)

  • Auto-wait — nearly zero flakiness by default
  • Trace viewer — visual replay of every failure
  • Built-in API testing — no extra dependency
  • Worker process isolation — no ThreadLocal needed
  • storageState — auth reuse across tests
  • Modern DX, fast to write, easy to debug

Selenium (Java counterpart)

  • Cross-browser: Chrome, Firefox, Safari, Edge, IE
  • Cloud grid: BrowserStack, SauceLabs, Selenium Grid
  • Java — same language as backend/enterprise teams
  • Mature ecosystem, 15+ years of community answers
  • Standard in enterprise QA hiring
  • Security scanning (Trivy) and unit tests included
Playwright's edge: developer experience, auto-wait, trace viewer, and unified API+UI in one tool. For most greenfield projects, it's the faster path to reliable tests.

Selenium's edge: cross-browser coverage, cloud grid integrations, Java ecosystem alignment, and — in this repo specifically — more mature CI with security scanning and unit tests for the infrastructure layer.

Mục tiêu thiết kế

Cùng triết lý 3 tầng với Selenium counterpart — infrastructure, abstraction, tests — nhưng thể hiện bằng TypeScript idioms. Pattern test.extend() thay thế inheritance: test khai báo đúng những gì nó cần và nhận qua injection, giúp dependencies rõ ràng và test body không còn setup noise.

Mục tiêu thứ hai là chứng minh rằng API testing và UI testing có thể sống trong cùng project, cùng ngôn ngữ, cùng fixture system — không cần dependency RestAssured riêng hay ngôn ngữ khác cho API.

Điểm tốt / Chưa tốt

Điểm tốt

  • Auto-wait — gần như không cần code wait thủ công
  • storageState auth — login 1 lần, dùng lại mọi test
  • test.extend() — fixtures compose sạch, không có chuỗi kế thừa
  • API + UI thống nhất — một import từ lib/fixtures
  • Trace on first retry — debug failure mà không cần tool thêm
  • TypeScript — types bắt lỗi refactoring lúc compile

Chưa tốt

  • ESLint không chạy trên CI — chỉ qua Husky, có thể bypass bằng --no-verify
  • Không có security scanning — không có Trivy hay npm audit
  • GHA chỉ trigger trên main/master — feature branch bỏ qua GHA
  • GeeksForGeeksHomePage tồn tại không có test — dead code
  • retries: 2 trên CI có thể che giấu flakiness thực sự
  • Không có unit tests cho tầng infrastructure/fixtures

Còn thiếu gì

  • Cao ESLint trong CI — lint chỉ chạy local qua Husky. Dev push với --no-verify là bỏ qua hoàn toàn. Cần thêm ESLint job vào GHA workflow.
  • Cao Security scanning — không có Trivy hay npm audit trong CI. Các dep như axios, googleapis, twilio chưa được scan CVE.
  • Cao GHA trigger trên mọi branch — hiện chỉ chạy trên main/master. Feature branch chỉ có CircleCI. Đổi thành branches: ["**"].
  • Vừa Test cho GeeksForGeeksHomePage — page object đã có, không có spec. Thêm test hoặc xóa dead code.
  • Vừa Video khi fail — trace bắt ở retry đầu nhưng không có video. Thêm video: 'on-first-retry' để debug trên CI phong phú hơn.
  • Thấp Unit tests cho fixtures — wiring trong pages.fixture.ts và defaults của env.config.ts chưa được test. Một unit test bắt misconfiguration trước khi nó hiện ra là lỗi test bí ẩn.
  • Thấp Locator ReqresHomePage — đang dùng "Your backend, live in your browser." có thể không khớp heading thực trên site. Cần verify lại với trang thật.
